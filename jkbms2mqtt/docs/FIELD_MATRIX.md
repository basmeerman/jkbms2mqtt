2. **V1.1** — [`specifications/BMS.RS485.Modbus.V1.1.pdf`](specifications/BMS.RS485.Modbus.V1.1.pdf), hand-transcribed.
3. **This repo** — `jkbms2mqtt/src/jkbms2mqtt/protocol/jk_modbus.py` and `jk_settings.py`. Citations are `file:line`.
4. **Phinix-org** — [Multiple-JK-BMS-by-Modbus-RS485](https://github.com/phinix-org/Multiple-JK-BMS-by-Modbus-RS485). ESPHome YAML.
5. **Jean** — [`upstream_reference/trame_specs.json`](../../upstream_reference/trame_specs.json), the field map for the proprietary 0x55AAEB90 BLE/UART frame Jean's Node-RED add-on uses. **Not Modbus.** Trame 1 = info block; Trame 2 = settings; Trame 3 = real-time. Frame layout has a 6-byte header, so Jean's byte = `spec_byte + 6`. Little-endian.

`—` = field not present / not decoded in that source.

## How to read the address columns

The specs use **byte offsets** within a block (e.g. `0x0004` in block `0x1000`).
The Modbus register address is `block_base + (byte_offset / 2)` — each field
occupies `length / 2` consecutive 16-bit Modbus registers, high word first.

- **This repo** stores `block_base + (byte / 2)` directly as the Modbus
  register address (e.g. `address=0x1002` for `VolCellUV`). The cited
  `RegisterDef.address` is that value.
- **Phinix** has two conflicting YAML conventions:
  - the `sensors/` files use `address: <block_base>` + `offset: <spec_byte>` (correct byte semantics);
  - the `numbers/` files use `address: <block_base + spec_byte>` directly (treating spec byte offset as a Modbus register count — which would address a different register under the spec's byte-based interpretation).

  Both forms appear active in their working device YAMLs. The matrix
  reports both literally; the effective Modbus reg depends on ESPHome's
  `offset` semantics for the YAML's `value_type`.
- **Jean** reads a single 300-byte frame the BMS streams in response to a
  Modbus 0x10 trigger; offsets are byte positions within that frame and
  values are decoded little-endian — a completely different protocol from
  the Modbus 0x03/0x10 reads the others use.

## Key deviations the matrix exposes

- **`TempBat3` / `TempBat4` / `TempBat5`** — spec V1.0 and V1.1 both place these at
  bytes `0xF8 / 0xFA / 0xFC` in the RT block → Modbus regs `0x127C / 0x127D / 0x127E`.
  This repo reads buffer offsets `0xF4 / 0xF5 / 0xF6` → regs `0x12F4 / 0x12F5 / 0x12F6`.
  Documented PB2A16S20P firmware deviation: the spec'd registers read zero
  on this firmware; the actual values live at the empirical addresses. See
  [`specifications/README.md`](specifications/README.md).
- **packed-bit register (`0x108A` per spec)** vs older code using `0x1114`.
  This repo now uses spec `0x108A`. Phinix's number/sensor files split: one
  variant uses `0x118A`, another the `0x1114` alias.
- **Phinix's two YAML conventions** noted above — internal inconsistency
  between the `sensors/` and `numbers/` files.
- **Several spec fields are not yet decoded by this repo** (TimeDcOCPR /
  TimeCOCPR / VolChargCur / RTCTicks / ODDRunTime / PWROnTimes …). Tracked
  as "—" in the **This repo** column for follow-up.
- **V1.0 vs V1.1 differences**: V1.1 adds the packed-bit BIT7–9
  (DisablePCLModule / TimedStoredData / ChargingFloatMode), reorganises the
  command block (`Shutdown` inserted at byte `0x04`, calibration encoding
  changes from `0.1V` to `mV` / `0.1A` to `mA`), and adds the
  LCD-buzzer / dry-contact / RCVTime / RFVTime settings to the info block.
  V1.0 has fields V1.1 dropped (TMPBatOTA/OTAR, ChargePWMDutyCyle,
  DischargePWMDutyCyle, PVDTrigTimestamps).
